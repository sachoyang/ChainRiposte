## 0. 전제 — 측정 없이는 아무것도 확정하지 않는다

지금까지 나온 것은 **코드와 설정을 읽어서 나온 후보**일 뿐 잰 값이 아니다.
아래 표의 "예상"은 전부 가설이고, 각 단계는 **측정 → 조치 → 재측정**으로 닫는다.

### 프로파일러 붙이는 법 (막혔던 지점)

폰은 처음부터 잘 붙어 있었다(`adb devices` → `R3CX10S7KXV`).
안 뜬 이유는 **빌드가 릴리스였기 때문**이다 — `EditorUserBuildSettings.development = False`.
릴리스 빌드에는 프로파일러가 붙을 구멍 자체가 없다.

| 항목 | 값 |
|---|---|
| Development Build | ✅ |
| Autoconnect Profiler | ✅ |
| Deep Profiling | ❌ (켜면 전부 느려져 진짜 병목이 묻힌다) |

측정 구간은 셋으로 고정한다 — 매번 같은 곳을 재야 비교가 된다:
**① 퍼즐 대기 중 ② 매치 연쇄 중 ③ 전투에서 노트가 밀려올 때.**

읽는 법: `VSync`가 두꺼우면 GPU 대기(→ 렌더 쪽), `Scripts`가 두꺼우면 CPU,
`GC Allocated in Frame`이 0이 아니면 그게 끊김의 원인이다.

## A. 프레임 (지금 범위)

### 이미 끝난 것 (세션 18 초반, 측정 전에 확정할 수 있었던 것)

| # | 무엇 | 근거 |
|---|---|---|
| A0-1 | **`Application.targetFrameRate = 60`** (`FrameRateBootstrap`) | 기본값 −1 = 플랫폼 기본값이고 **안드로이드에서 그건 30**이다. 모바일은 `vSyncCount`가 무시되므로 이게 유일한 손잡이 |
| A0-2 | **URP HDR 끔** (`m_SupportsHDR: 1 → 0`) | 2D 도트에 1을 넘는 밝기가 없다. 얻는 것 없이 렌더 타깃 정밀도만 올라가 대역폭을 먹는다 |

A0-1은 성능만의 문제가 아니다 — 30fps면 한 프레임 33ms가 **Lv0 패링 판정 폭(0.25초)의 13%**다.
정확히 눌러도 프레임 경계에 걸려 놓치는 일이 생긴다.

### A1. 측정 기준선

Development Build로 폰에 올리고 세 구간의 **fps · CPU/GPU 비중 · 프레임당 GC**를 적어 둔다.
이 표가 없으면 뒤 단계의 "좋아졌다"가 느낌일 뿐이다.

**산출물**: 이 문서 §A1 표에 숫자 기입.

### A2. 포스트 프로세싱을 옵션으로

**지금**: `PostFxBootstrap`이 `Awake`에서 `renderPostProcessing = true`를 켜고
FilmGrain + Vignette를 얹는다. **끄는 방법이 없다.**

모바일에서 전체 화면 패스는 단일 최대 비용이고, 그레인은 픽셀마다 노이즈를 샘플링한다.

**할 것**
- `GameOptions`에 화면 효과 항목 추가(저장은 기존 옵션과 같은 경로)
- 설정 패널에 토글 한 줄 — **프리팹 하나만 고치면 세 씬이 같이 바뀐다**(세션 14 ⑬)
- 기본값은 측정 결과로 정한다. GPU 병목이면 모바일 기본 끔

**왜 지우지 않고 옵션인가**: GDD §7의 톤이다. 성능 때문에 연출을 영구히 버리는 것은
기기가 좋아지면 손해다. **끌 수 있게** 만드는 것이 답이다.

### A3. 로딩 화면 + 미리 굽기 (사용자 요청)

가장 큰 덩어리. **런타임에 굽느라 끊기는 것들을 로딩 화면 뒤로 몰아넣는다.**

#### 지금 런타임에 굽는 것

| 무엇 | 비용 | 언제 튀나 |
|---|---|---|
| **TMP 한글 글리프** (`neodgm SDF` = Dynamic + `ClearDynamicDataOnBuild: 1`) | SDF 래스터화 (CPU) | 빌드에 아틀라스가 **빈 채로** 나가서, 기기에서 글자가 **처음 뜰 때마다** |
| **노트 원 텍스처** (`PlaceholderSprite.Annulus`) | 256×256 RGBA32 × 약 11장. 장당 65,536픽셀 루프 + GPU 업로드 | 전투 첫 2초에 몰린다 |
| 그 외 `PlaceholderSprite` 생성물 (검기·띠·마스크) | 같은 성격 | 처음 쓰일 때 |

#### 폰트가 특히 중요한 이유

**게임에 나오는 글씨의 원천이 `Localization.csv` 한 장이다.**
그래서 "이 게임에 쓰이는 글자"를 **정확히 알 수 있다** — CSV를 훑어 문자 집합을 뽑으면 끝이다.
원천이 하나라는 구조가 여기서 그대로 값을 한다.

#### 로딩 화면 (사용자 지정)

- UI는 **슬라이더 바 하나**. 본 게임에 쓰인 에셋 재사용(`panel`, `bar_container_a`, `box_small`)
- 진행률은 **가짜로 흘리지 않는다** — 실제 작업 단위로 채운다
- 문구는 당연히 현지화 키로. 하드코딩 금지
- 씬 오서링 원칙대로 **빌더 메뉴가 실물을 한 번 깔고** 이후 씬에서 편집

#### 구현 결과 ✅

**위치**: 인트로 씬 안. **로고가 도는 동안 뒤에서 굽고**, 로고가 끝났는데도 남아 있을 때만
바를 띄운다 → **대개는 바가 안 보이는 것이 정상**이다. 굽는 일을 로고 뒤에 세우면
대기가 그대로 늘어나므로 겹쳐 두는 것이 요점.

**실측**: CSV 문구 **270개**(135키 × 2언어) → 고유 글자 **343자**(한글 **274**).
`AlwaysNeeded`를 더해 440자 안팎을 48자씩 열 번 남짓에 나눠 굽는다.
`GlyphBatch`는 총 시간이 아니라 **한 프레임의 무게**를 정한다 — 크게 잡으면 로고가 튄다.

| 파일 | 역할 |
|---|---|
| `Game/Flow/Prewarmer.cs` | 실제로 굽는다. 진행률을 (0~1, 현지화 키)로 보고 |
| `Game/Flow/LoadingScreen.cs` | 바 + 인트로 연동. 진행률은 **실제 작업 단위**로 찬다 |
| `Editor/LoadingScreenBuilder.cs` | `Tools ▸ ChainRiposte ▸ Add Loading Screen To Intro` (비파괴) |
| `Loc.AllDisplayValues()` | 모든 언어의 모든 문구 — 글자를 뽑는 창구 |

**설계 판단**
- **진행률을 시간으로 흘리지 않는다.** 느린 기기에서 바가 다 찬 채로 멈춰 있으면 "멈췄다"로 읽힌다
- **모든 언어를 굽는다.** 언어는 옵션에서 중간에 바뀌고, 그때 안 구운 글자를 만나면 그 화면에서 끊긴다
- **폴백 폰트까지 굽는다.** 기본 폰트에 없는 글자가 폴백에서 처음 발견될 때 똑같이 끊긴다
- **빗나가도 무해하다.** 캐시 워밍이라 잘못 짚으면 도움이 안 될 뿐 고장 나지 않는다 →
  노트 원 비율 범위를 `CombatScreen`에서 끌어오는 배선을 **일부러 안 만들었다**(그 배선이 더 깨지기 쉽다)
- `IntroController`의 슬롯이 비면 **곧장 타이틀로** 간다 — 인트로는 단독 실행이 가능해야 한다

**⚠ 남은 것**: 현지화 키 4개(`loading.text` / `loading.font` / `loading.combat` / `loading.done`)를
**구글 시트에 넣고 다시 구워야 한다.** 그 전까지는 바 위에 생 키가 뜬다.

### A4. 렌더 해상도 다이얼

`m_RenderScale: 1.0` — 고해상도 폰에서 네이티브 픽셀을 전부 그린다.
도트 게임이라 0.8로 내려도 잘 티가 안 난다. **A1 측정에서 GPU 병목이 확인되면만** 한다.

⚠️ 도트가 흐려질 수 있어 눈으로 확인이 필요하다. 성능이 CPU 병목이면 이 단계는 **건너뛴다**.

## A-보류. 측정 결과에 따라 판단할 것

| 무엇 | 왜 지금 안 하나 |
|---|---|
| **Linear → Gamma 색공간** | 모바일에서 Gamma가 싸지만 **게임 전체 색이 달라진다.** 성능만 보고 건드릴 값이 아니다 |

## A-확인함, 문제 없음 (여기 파지 말 것)

`m_RequireDepthTexture: 0` · `m_RequireOpaqueTexture: 0`(전체 화면 복사 없음) ·
MSAA 꺼짐 · SRP Batcher 켜짐 · IL2CPP + ARM64 ·
`Update`/`LateUpdate` 14개 전부 가볍고 상한이 있음 ·
매 프레임 TMP 텍스트를 쓰는 곳 없음(캔버스 재빌드 없음) ·
`BoardView.LateUpdate`의 스포트라이트는 튜토리얼 전용이라 지금은 비용 0.
