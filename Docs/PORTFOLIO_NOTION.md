# ChainRiposte

## 프로젝트 소개

> 매치3 퍼즐로 준비하고, 리듬 패링으로 실력을 증명하는 2D 모바일 로그라이트

퍼즐과 보스전을 번갈아 진행하는 게임입니다. 퍼즐에서 캔 소울로 성장하고, 그 판에서 잃은 체력을 그대로 들고 보스전에 들어갑니다. **두 장르를 하나의 자원으로 이어** 퍼즐이 "쉬어 가는 구간"이 되지 않도록 설계했습니다.

기획부터 클라이언트 구현, 데이터 설계, 에디터 툴 제작까지 **1인으로 개발**했으며, 전투·퍼즐 로직 전체를 UnityEngine에 의존하지 않는 순수 C#으로 분리해 **에디터 없이 3초에 도는 테스트 167개**로 검증했습니다.

## 주요 구현 내용

### (아키텍처) 순수 C# 코어와 Unity 어댑터 분리

#### 개요

게임 로직을 `MonoBehaviour` 안에 두면 로직을 검증할 때마다 에디터를 켜고 씬을 실행해야 합니다. 특히 이 프로젝트는 판정 타이밍과 보드 낙하 규칙처럼 **반복 검증이 필요한 규칙이 많아**, 검증 비용이 높으면 규칙을 고치는 일 자체를 피하게 되는 문제가 있었습니다.

또한 "로직에 Unity를 쓰지 말자"는 규칙은 문서로만 적어 두면 개발이 급할 때 반드시 깨집니다. 이를 해결하기 위해 **어셈블리를 분리하고 의존 방향을 컴파일러가 강제하도록** 구성했습니다.

#### 설계

- **어셈블리 4개로 계층 분리**
  - `Core`(순수 C#) → `Game`(Unity 어댑터) → `Editor`(툴) 단방향 의존
  - `Core`의 asmdef에 **`noEngineReferences: true`** 를 지정해 UnityEngine 참조 자체를 차단
  - 규칙 위반이 리뷰가 아니라 **빌드 에러**로 드러납니다
- **경계를 넘는 방법을 세 가지로 고정**
  - 밸런스 수치는 전부 ScriptableObject → `ToConfig()`로 순수 C# config 변환 (Adapter)
  - Unity 전용 타입은 `Func<>`로 감싸 주입 (`AnimationCurve` → `Func<float,float>`)
  - Core는 결과를 C# event로만 발행하고, 누가 구독하는지 알지 않습니다 (Observer)
- **조립 지점을 한 곳으로**
  - `GameManager`를 Composition Root로 두고 `[DefaultExecutionOrder(-100)]`로 초기화 순서를 고정

```
ChainRiposte.Editor   19 파일 / 4,814줄   에디터 툴
        │
ChainRiposte.Game     76 파일 / 12,743줄  Unity 어댑터 (UI · VFX · 입력 · 저장)
        │  ← 단방향
ChainRiposte.Core     59 파일 / 5,299줄   순수 C# 로직 (UnityEngine 참조 0)
```

이 구조 덕분에 테스트 167개가 **에디터 없이 3초에** 돌고, 후반에는 Unity를 켜지 않고 `dotnet` 콘솔 프로그램으로 퍼즐 로직을 대량 검증할 수 있었습니다. (아래 트러블슈팅 참조)

### (전투) 채보 기반 패링 전투와 결정적 시뮬레이션

#### 개요

보스 공격을 코드로 하드코딩하면 패턴을 하나 고칠 때마다 빌드해야 하고, 난이도 조정이 프로그래머 작업이 됩니다. 또한 판정을 프레임 단위로 처리하면 **기기 성능에 따라 같은 입력이 다른 결과**를 내는 문제가 있었습니다.

이를 해결하기 위해 보스 공격을 **박(beat) 단위 노트 데이터**로 분리하고, 전투 진행을 프레임이 아니라 **상태 경계 단위로 끊어 계산**하도록 구현했습니다.

#### 설계

- **공격 = 채보 데이터**
  - 노트 하나 = 타격 시점(박) + 예비동작 길이 + 피해 배율
  - **연속기를 별도 타입으로 만들지 않았습니다** — 노트를 촘촘히 찍으면 그것이 연속기입니다
  - HP 구간별 채보 풀 + 가중 무작위로, 같은 보스도 체력에 따라 패턴이 험해집니다
- **페이즈를 2층으로 분리**
  - `인살 페이즈` — 처형 1회 분량. 겉모습·게이지가 통째로 교체
  - `HP 구간 페이즈` — 같은 모습으로 채보만 교체
  - 페이즈를 안 나눈 보스는 1페이즈로 감싸 처리해, 전투 코드에 "페이즈가 있는 보스 / 없는 보스" 분기가 생기지 않도록 했습니다
- **결정적 진행**
  - 프레임 delta를 그대로 흘리지 않고 **다음 상태 경계(타격 시점·판정 만료)까지만** 진행
  - 같은 입력이면 프레임레이트와 무관하게 같은 결과가 나옵니다

```csharp
// 상태 경계마다 끊어서 진행한다.
private const float TimeEpsilon = 1e-4f;
step = Math.Max(step, TimeEpsilon);   // 0초 경계에서 제자리걸음(무한 루프) 방지
```

- **전투 규칙과 연출 길이를 분리**
  - 처형 후 다음 페이즈로 넘어갈 때 Core는 `AwaitingPhaseTransition` 상태로 시간을 멈추고, 컷신이 끝나면 Game이 재개시킵니다
  - Core가 컷신 길이를 알면 연출을 바꿀 때마다 전투 규칙을 고쳐야 하기 때문입니다

### (퍼즐) 매치3 엔진 — 모델은 기록하고, 뷰는 재생만 한다

#### 개요

매치3는 한 번의 스왑이 매치 → 파괴 → 낙하 → 리필 → 연쇄 매치로 이어집니다. 이 과정을 연출과 함께 진행하면 **연출이 도는 동안의 중간 상태**가 생겨, 연출 길이를 바꿀 때마다 게임 로직이 흔들리는 문제가 있었습니다.

이를 해결하기 위해 엔진이 **모든 연쇄를 먼저 끝내고 완결된 기록을 한 번에 반환**하고, 뷰는 그 기록을 시간순으로 재생만 하도록 분리했습니다.

#### 설계

- **완결 기록 반환 구조**

```
PuzzleEngine.Swap(a, b) → SwapResult (캐스케이드 · 낙하 · 기믹 이벤트 전부 포함)
                                ↓
                     BoardView가 코루틴으로 재생만 한다
```

  - 연출 중에도 모델은 이미 최종 상태 → 연출 길이를 바꿔도 로직이 안 흔들립니다
  - 연출을 통째로 스킵해도 게임 상태가 동일합니다
- **비정형 보드 지원**
  - 하트·해골처럼 구멍 뚫린 보드에서 구멍이 대각 슬라이드를 끊지 않도록 처리
  - 벽에 얹힌 타일이 대각선 아래로 미끄러져 **벽을 우회해 하강**
- **데드락 검출 + 리롤**
  - 매치가 나지 않는 스왑은 턴을 소모하지 않으므로, 둘 수 있는 수가 없으면 게임이 멈춥니다
  - `MoveFinder`로 검출한 뒤 **턴을 소모하지 않고** 보드를 섞습니다 (벽·보스·기믹 타일은 제자리 유지)

#### 확장 구조 — 기믹은 조합 가능한 모듈로

스테이지마다 다른 규칙(전염·시한폭탄·사슬결박·성난몬스터)을 엔진 분기로 넣으면 스테이지가 늘 때마다 엔진이 커집니다. 엔진은 **훅 5개만 열고**, 규칙은 각 모듈이 갖도록 구성했습니다. (Strategy + Composite)

```csharp
public interface IStageGimmick
{
    void OnBoardInitialized(GimmickContext ctx);                            // 씨앗 심기
    void OnTilesSpawned(GimmickContext ctx, IReadOnlyList<TileSpawn> s);    // 폭탄 · 사슬 부착
    void OnMatchesResolving(GimmickContext ctx, HashSet<GridPos> cleared);  // 파괴 목록 수정
    void OnTurnEnded(GimmickContext ctx);                                   // 확산 · 카운트다운
    void OnTimeElapsed(GimmickContext ctx, float deltaSeconds);             // 실시간 위협
}
```

- 기믹 4종이 **서로를 모른 채 조합**됩니다 (기본 클래스에서 빈 구현을 제공해 필요한 훅만 재정의 — Template Method)
- `OnMatchesResolving`이 파괴 목록을 **수정할 수 있게** 한 것이 핵심입니다 → "사슬 타일은 매치되어도 파괴 대신 사슬만 풀린다"를 엔진 수정 없이 구현
- **마지막 훅은 설계 실패에서 나왔습니다** — 턴 훅만 있을 때는 *아무 수도 두지 않는 것이 가장 안전한 플레이*가 되어 버렸습니다. 시간 기반 훅을 추가해 가만히 있어도 위협이 자라도록 수정했습니다

### (툴) 에디터 툴링 — 전체 코드의 18%

#### 개요

채보 하나를 확인하려면 인스펙터에서 노트를 찍고, 플레이해서 퍼즐을 클리어하고, 보스전까지 도달해야 했습니다. **확인 한 번에 2~3분**이 들어 튜닝을 시도하는 횟수 자체가 줄어드는 문제가 있었습니다.

반복 확인이 필요한 작업을 골라 에디터 툴로 만들었고, 결과적으로 전체 코드의 18%(19파일 / 4,814줄, 메뉴 34종)가 툴 코드입니다.

#### 설계

- **채보 에디터** — 타임라인에서 클릭·드래그로 노트 배치, 스냅(1 · 1/2 · 1/4박), 예비동작을 막대로 시각화, **▶ 미리듣기**
  - 확인 절차가 `노트 찍기 → 플레이 → 퍼즐 클리어 → 보스전 도달`(2~3분)에서 `노트 찍기 → ▶ 클릭`(2초)으로 단축
- **보드 그리드 에디터** — 문자열 대신 격자를 칠해 보드를 편집
  - 인스펙터와 전용 창 두 곳에서 편집할 수 있게 하되, **그리는 코드는 한 벌**만 두고 공유했습니다 (브러시를 하나 늘릴 때 두 곳을 고치면 반드시 한쪽을 잊습니다)
  - 반대로 **편집 상태는 호스트마다 따로** 갖게 했습니다 — static으로 두면 두 창을 함께 열었을 때 서로 덮어써 드래그가 끊깁니다
- **현지화 툴** — 구글 시트 → CSV 동기화, **씬을 훑어 CSV에 없는 키를 검출**
- **아트 정규화 툴** — 스프라이트 여백을 자동 트리밍해 타일 크기 통일, 눌림 스프라이트 일괄 배선

#### 툴을 만들며 세운 원칙

- **두 번 실행해도 무해해야 합니다** — 일괄 교체 툴이 두 번째 실행에서 껍데기를 겹쳐 씌운 사고 이후, 조상 노드 제외 + 이미 처리된 대상 건너뛰기로 이중 방어했습니다
- **툴에도 고유명사를 적지 않습니다** — 눌림 스프라이트는 `btn_wide` → `btn_wide_pressed` **이름 규칙**으로 탐색하므로, 아트가 늘어도 툴을 수정하지 않습니다
- **씬을 코드로 생성하는 빌더는 만들지 않습니다** — 수명이 며칠이고 이후에는 손으로 배선한 값을 날리는 위험만 남습니다. 실제로 후반에 그런 빌더 15개를 삭제해 에디터 코드를 8,637줄 → 4,814줄로 줄였습니다

### (Trouble Shooting) 눈에 보이는 것과 실제 판정이 어긋난다

#### 문제 상황

패링 판정이 "분명히 맞춰서 눌렀는데 실패"하는 경우가 반복적으로 발생했습니다. 리듬 게임에서 **플레이어가 실패 원인을 알 수 없는 것**은 가장 치명적인 결함이라 우선순위를 높여 처리했습니다.

#### 문제와 해결

**[ 노트 원의 두께만큼 판정이 밀려 있던 문제 ]**

- **문제**: 노트 원이 판정 띠에 겹쳐 보이는데도 판정이 나지 않는 구간이 존재
- **원인**: 노트 원은 **두께가 있는 그림**인데, 판정은 그 원의 **바깥 테두리** 위치를 기준으로 계산하고 있었습니다. 보이는 겹침과 실제 판정 사이에 **원 두께만큼의 오차**가 그대로 존재했습니다
- **해결 과정**:
  1. 노트의 위치 기준을 원의 **안쪽 테두리**로 재정의
  2. 판정 띠의 반지름을 판정 수치에서 직접 계산 (`바깥 = 1 + 판정윈도우 × 속도`, `안쪽 = 1 − 늦은유예 × 속도`)
  3. 노트 원 텍스처를 그 두께 비율에 맞춰 런타임 생성하도록 변경
  4. 실제 아트로 교체할 때를 위해 원의 구멍 비율을 인스펙터 값으로 노출
- **결과**: **보이는 겹침이 곧 판정**이 되었습니다. 부수 효과로 PARRY 스탯을 올리면 판정 띠가 눈에 띄게 굵어져, 성장이 수치가 아니라 화면으로 드러납니다
- **한계**: 실제 아트 스프라이트로 교체하면 자동 생성을 끄고 그 그림의 비율을 직접 입력해야 합니다. 현재는 절차만 문서화한 상태입니다

> **같은 숫자를 로직과 뷰 두 곳에 적으면 반드시 어긋납니다. 한 곳에서 파생시키면 어긋날 수가 없습니다.**

> 📸 **[스크린샷]** PARRY 0 / PARRY 최대의 판정 띠 두께 비교 2장 — 이 항목은 비교 이미지가 설명을 대신합니다

### (Trouble Shooting) 주석이 주장하던 불변식이 거짓이었다 — 벽 밑에 빈 칸

#### 문제 상황

퍼즐 보드에서 벽 아래에 타일이 채워지지 않는 칸이 남아, 의도하지 않은 구멍이 뚫린 것처럼 보이는 현상이 발생했습니다.

코드 주석은 *"벽과 비활성 셀 이외의 모든 칸은 항상 채워진다"* 고 **주장**하고 있었고, 비정형 보드 퍼즈 테스트도 통과하고 있었습니다. 손으로 고른 보드에서만 참인 불변식이었고, **테스트가 있다는 사실이 오히려 문제를 늦게 발견하게 만들었습니다.**

#### 문제와 해결

**[ 도달 가능한 타일이 존재하지 않는 칸 ]**

- **문제**: 특정 배치에서 중력·슬라이드로는 절대 채울 수 없는 칸이 남음
- **원인**: 대각 슬라이드는 **한 칸짜리 이동**이라 출처가 정확히 대각선 위 칸이어야 하는데, 그 자리가 ①벽 ②보드 밖 ③위가 비어 있는 구멍이면 가져올 타일이 물리적으로 존재하지 않습니다. **가장 흔한 경우가 "부서진 벽이 남긴 자리"** 로, 특수 지형이 아니라 일반 플레이 중에 발생했습니다
- **해결 과정**:
  1. Core에 UnityEngine 의존이 없다는 점을 이용해, **에디터 없이 `dotnet` 콘솔로 무작위 보드 60,000개**를 검사하는 하네스를 작성해 반례를 수집
  2. 첫 해법(그 자리에서 새 타일 생성)은 낙하와 다른 별도 연출이 필요해 보드 정착 흐름에서 분리되는 문제가 있어 폐기
  3. 발상을 전환 — 갇힌 칸으로 **올 수 있는 타일은 없지만, 그 칸에서 리필 입구까지 이어지는 경로는 대개 존재**한다는 점을 이용
  4. BFS(8방향)로 경로를 찾아 경로 위의 타일을 한 칸씩 밀면, **구멍이 반대 방향으로 이동해 보드 최상단에 도달**하고 그 자리는 평소처럼 리필이 채웁니다
- **결과**: 갇힌 칸의 **99.08%**가 이 경로로 해결됩니다(나머지 0.92%는 벽에 완전히 둘러싸인 칸으로 제자리 생성). 무작위 보드 60,000개 검사에서 위반 0건, 회귀 테스트 4개를 추가해 163 → 167개가 되었습니다
- **특기 사항**: **뷰 코드는 한 줄도 수정하지 않았습니다.** 이 이동이 일반 타일 이동으로 기록되기 때문에 기존 낙하 연출이 경로를 꺾어 그대로 재생합니다 — 모델/뷰를 분리해 둔 설계가 값을 한 지점입니다

---

**[ 새 규칙이 기존 규칙과 충돌해 무한 루프 ]**

- **문제**: 수정 이후 특정 배치에서 보드 정착이 끝나지 않고 웨이브 상한(200)을 모두 소모
- **원인**: 갇힌 칸의 타일이 **벽에 얹혀 있는 경우**, 기존 슬라이드 규칙은 그 타일을 밖으로 내보내려 하고 새로 넣은 끌어오기 규칙은 다시 안으로 당겨, 타일 하나가 두 칸 사이를 무한히 왕복했습니다
- **해결 과정**:
  1. 퍼즈 하네스에서 반례 배치를 재현
  2. 같은 구멍은 **한 번의 정착에서 한 번만** 끌어오도록 제한
  3. 그래도 남는 칸은 제자리 생성 경로로 위임
- **결과**: 반례 배치의 소모 웨이브가 **200 → 4**로 감소
- **한계**: 특수 타일(보스·사슬·폭탄)은 갇힌 칸에 배치되면 해결 불가능한 상태가 되므로 **별도 규칙으로 제외**하고 있습니다. 재추첨 방식으로 막으려 했다가 실측에서 16칸 중 8칸이 통과해(`0.9⁹ ≈ 39%`) 확률이 아닌 확정 규칙으로 바꿨습니다

> **주석에 적어 둔 불변식은 주장이지 보장이 아닙니다. 보장하려면 반례를 찾으러 가야 합니다.**

> 📸 **[스크린샷]** dotnet 퍼즈 하네스 실행 결과 콘솔 (`검사 60,000판 / 위반 0건`)

### (Trouble Shooting) 최적화가 화면의 글씨를 통째로 날렸다

#### 문제 상황

한글 폰트가 동적 아틀라스 방식이라 새 글자가 처음 표시될 때마다 SDF 생성이 일어나 화면 전환마다 끊김이 있었습니다. 시작 로딩에서 모든 글자를 미리 생성하도록 개선했는데, **실기 빌드에서 일부 글자가 아예 표시되지 않는** 문제가 발생했습니다. 에디터에서는 정상이었습니다.

#### 문제와 해결

**[ 사전 생성이 아틀라스 용량을 넘긴 문제 ]**

- **문제**: 개선 이후 실기에서만 일부 글자가 렌더링되지 않음
- **원인**: 폰트 아틀라스가 1024×1024 **한 장**인데 386자를 한 번에 생성하면서 **두 번째 아틀라스로 넘어갔고**, 넘친 글자가 기기에서 그려지지 않았습니다. 이전에는 화면에 실제로 등장한 글자만 조금씩 생성되어 **우연히 한 장 안에 들어가 있었을 뿐**이었고, 즉 **사전 생성 자체가 방아쇠**였습니다
- **해결 과정**:
  1. 실기 로그로 생성 요청 글자 수와 아틀라스 장수를 실측
  2. 아틀라스를 2048×2048로 확대해 386자가 한 장에 들어가는 것을 확인
  3. **아틀라스가 두 장을 넘으면 에러 로그를 출력**하도록 방어 코드 추가
- **결과**: `요청 386자 / 누락 0자 / 아틀라스 1장`으로 정상화. 생성할 글자 수를 정확히 알 수 있었던 이유는 **화면 문구의 원천이 현지화 CSV 한 장뿐**이기 때문입니다 (실측 343자, 한글 274자)
- **한계**: 아틀라스 크기를 늘리는 방식이라 문구가 크게 늘면 다시 넘칠 수 있습니다. 넘침을 **에러로 드러나게** 해 두었을 뿐 자동 분할은 구현하지 않았습니다

> **설계 당시 "캐시를 미리 데우는 작업이라 빗나가도 무해하다"고 판단했는데, 폰트에는 해당되지 않았습니다.
> "무해한 최적화"라는 판단 자체가 검증 대상이었습니다.**

**참고 — 같은 작업에서 함께 개선한 항목**

| 원인 | 실제 문제 | 조치 |
| --- | --- | --- |
| 30fps 상한 | `Application.targetFrameRate` 미지정. 기본값 −1은 **모바일에서 30fps** | 60 고정 |
| HDR | 2D 도트에 1을 넘는 밝기가 없는데 렌더 타깃 정밀도만 상승 | URP에서 비활성화 |
| BGM 용량 | PCM WAV 6곡 125MB가 빌드에 그대로 포함 | Streaming / Vorbis (단발 효과음은 반대로 DecompressOnLoad) |

> 30fps 상한은 성능만의 문제가 아니었습니다. 한 프레임 33ms는 **Lv0 패링 판정 폭(0.25초)의 13%** 로,
> 정확히 입력해도 프레임 경계에서 놓치는 경우가 발생합니다. 설정 하나가 게임의 핵심 조작감을 깎고 있었습니다.

## 기타 구현 내용

*(노션에서 각 항목을 토글로 접으면 깔끔합니다)*

**현지화 시스템**
- 구글 시트 → CSV 한 장을 원천으로 삼고, 코드·씬에 문자열을 하드코딩하지 않았습니다
- 정적 문구는 바인더 컴포넌트 + 키, 동적 문구는 조회 API + 언어 변경 이벤트 구독으로 재렌더합니다
- 동적 문구에 바인더를 붙이면 언어 전환 시 서로 덮어쓰는 문제가 있어, **값이 아니라 키를 교체**하는 방식으로 통일했습니다

**세로 / 가로 화면 동시 지원**
- UI 요소마다 세로·가로 프리셋 2벌을 갖게 하고, 해상도 변화를 감지해 전환합니다
- 배치 값은 코드가 아니라 **씬에서 드래그해 저장**하는 에디터 버튼으로 잡습니다

**세이브 데이터 버전 마이그레이션**
- 진행도·런 상태를 v1 → v2 → v3으로 확장하면서 구버전 세이브를 자동 변환합니다
- 이월되는 값과 판 단위 값을 구분하는 것이 핵심이었습니다 (아래 트러블슈팅 참고 항목)

**난이도 커브와 회차(NG+)**
- 스테이지별 난이도 표를 작성하지 않고 **고리 깊이 × 증가율로 계산**합니다 — 스테이지를 추가해도 표를 갱신할 필요가 없습니다
- 원본 보스 데이터를 수정하지 않고 배수를 곱한 **새 config를 생성**합니다 (같은 에셋을 공유하는 다음 판이 부풀려진 값을 다시 부풀리는 것을 방지)

**런타임 안정성**
- 오디오 클립·스프라이트 슬롯이 비어 있어도 진행이 멈추지 않도록 처리 — 배선이 덜 된 상태로도 플레이 가능해야 1인 개발에서 병목이 생기지 않습니다
- 도메인 리로드 비활성 환경에 대비해 정적 서비스 전체에 초기화 훅을 두었습니다
