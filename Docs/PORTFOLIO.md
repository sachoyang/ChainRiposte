## 1. 게임 소개

### 한 판의 흐름

```
월드맵 → 퍼즐(매치3) → 준비(스탯 분배) → 보스전(패링) → 클리어 → 다음 고리
                 ↑                                    ↓ 죽으면
                 └──────────── 사슬만 끊기고 성장은 남는다 ────┘
```

### 두 장르를 한 판에 붙인 이유

- **퍼즐 = 준비 구간**: 소울을 캐서 레벨업하고, 보스전에 가져갈 HP를 지킨다
- **보스전 = 실력 구간**: 성장으로 벽을 낮출 수는 있어도 **대신 눌러 주지는 않는다**
- 퍼즐에서 맞은 HP가 그대로 보스전으로 이어진다 → **두 장르가 하나의 자원으로 연결**

### 핵심 설계 원칙

> **난이도는 실행(패링)에서 오고, 성장은 모서리만 깎는다.**

성장이 난이도를 완전히 지우면 퍼즐이 무의미해지고, 성장이 아무것도 안 하면 퍼즐이 무의미해진다. 이 한 줄이 모든 밸런스 수치의 기준이 되었다.

## 3-1. 데이터 흐름

```
[기획 데이터]            [경계]              [순수 로직]           [표현]
ScriptableObject  ──ToConfig()──►  Core Config  ──►  Core System
 (인스펙터 편집)      Unity 타입을         (순수 C#)          │
                     Func<>로 감쌈                          │ C# event
                                                            ▼
                                              Game 어댑터 → UI / VFX / SFX
```

### 경계를 넘는 규칙 3가지

1. **밸런스 수치는 전부 ScriptableObject** — 코드에 상수로 박힌 밸런스가 없다
2. **Unity 타입은 `Func<>`로 감싼다** — `AnimationCurve` → `Func<float, float>`
   → Core가 커브를 "값을 돌려주는 함수"로만 알므로 Unity를 몰라도 된다
3. **Core는 이벤트로만 말한다** — 25종 C# event. Core가 Game을 참조하지 않고도 화면이 반응한다

## 4. 적용한 디자인 패턴

패턴 이름을 먼저 정하고 끼워 맞춘 게 아니라, **문제가 먼저 있고 그 해법이 패턴이었던 것**만 적었다.

| 패턴 | 적용 위치 | 해결한 문제 |
|---|---|---|
| **Strategy + Composite** | `IStageGimmick` (기믹 4종) | 스테이지 기믹을 **조합 가능**하게. 엔진은 훅 5개만 열고 규칙은 모듈이 갖는다 |
| **Template Method / Null Object** | `abstract class StageGimmick` | 훅 5개 중 **필요한 것만 override**. 안 쓰는 훅 때문에 빈 메서드를 적지 않는다 |
| **Adapter** | `~SO.ToConfig()` | Unity 직렬화 타입 ↔ 순수 C# config. 경계가 이 메서드 하나뿐이라 찾기 쉽다 |
| **Observer** | Core의 event 25종 | 단방향 의존을 지키면서 역방향 통지. Core는 누가 듣는지 모른다 |
| **Composition Root** | `GameManager` `[DefaultExecutionOrder(-100)]` | 객체 조립을 한 곳에서. 의존성 주입 지점이 하나 |
| **Memento** | `RunState` · `PlayerStatsSnapshot` | 런 상태 스냅샷/복원 + **버전 마이그레이션**(v1→v2→v3) |
| **Decorator (변형)** | `BossConfigScaler` | 난이도 배수를 곱해 **새 config를 만든다**. 원본을 제자리에서 고치면 같은 에셋을 쓰는 다음 판이 이미 부푼 값을 또 부풀린다 |
| **Factory Method** | `TileView.Create` · `ExplosionView.Create` | 데이터로 개수가 정해지는 뷰의 생성 규칙을 한 곳에 |
| **Service Locator** | `static class` 17종 | 씬을 넘나드는 저장·조회·전달. GameObject가 아니므로 `DontDestroyOnLoad`가 **단 2개**로 줄었다 |
| **Flyweight (성격)** | `TileDefinition` | 타일 수백 개가 정의 인스턴스를 공유 |

### 특히 자랑하고 싶은 것 — 기믹 Strategy

```csharp
public interface IStageGimmick
{
    void OnBoardInitialized(GimmickContext ctx);                    // 씨앗 심기
    void OnTilesSpawned(GimmickContext ctx, IReadOnlyList<TileSpawn> s); // 폭탄/사슬 붙이기
    void OnMatchesResolving(GimmickContext ctx, HashSet<GridPos> cleared); // 파괴 취소/추가
    void OnTurnEnded(GimmickContext ctx);                           // 확산/카운트다운
    void OnTimeElapsed(GimmickContext ctx, float deltaSeconds);     // 실시간 위협
}
```

- 기믹 4종(전염 · 시한폭탄 · 사슬결박 · 성난몬스터)이 **서로를 모른 채 조합**된다
- `OnMatchesResolving`이 파괴 목록을 **고칠 수 있게** 한 것이 열쇠 → 사슬은 "파괴 대신 사슬만 풀림"을 엔진 수정 없이 구현
- **마지막 훅 `OnTimeElapsed`는 설계 실패에서 나왔다**: 턴 훅만 있으니 *손을 놓고 있는 것이 가장 안전한 수*가 되어 버렸다. 실시간 훅을 추가해 "가만히 있어도 위협이 자라게" 고쳤다

## 5. 어필 기술 ① — 리듬 패링 전투

### 채보(악보) 기반 전투 시스템

- 보스 공격을 **박(beat) 단위 노트**로 찍는다: 타격 시점 · 예비동작 길이 · 피해 배율
- **연속기는 별도 타입이 아니다** — 노트를 촘촘히 찍으면 그게 연속기
- HP 구간별 채보 풀 + 가중 무작위 → 같은 보스도 체력에 따라 험해진다
- 인살(처형) 페이즈 2층 구조: `인살 페이즈`(겉모습·게이지 교체) ▸ `HP 구간 페이즈`(채보만 교체)

### 결정적(deterministic) 시뮬레이션

```csharp
// 상태 경계(타격 시점 · 윈도우 만료)마다 끊어서 진행한다.
private const float TimeEpsilon = 1e-4f;
step = Math.Max(step, TimeEpsilon);  // 0초 경계에서 제자리걸음 방지
```

- 프레임 단위로 흘리지 않고 **다음 상태 경계까지만** 진행
- → **프레임레이트와 무관하게 같은 입력이면 같은 결과**
- → 엔진 없이 순수 C#으로 전투 전체를 테스트할 수 있다

## 5-2. 어필 기술 ② — "보이는 것 = 판정"

### 발견한 문제

패링 판정 UI에서 **눈에 보이는 것과 실제 판정이 어긋나 있었다.**

- 흰 원은 **두께가 있는 그림**인데, 판정은 그 원의 **바깥 테두리** 위치로 계산
- → "띠에 걸친 것처럼 보이는데 아직 판정 밖"인 구간이 **원 두께만큼 통째로** 존재
- 플레이어는 자기가 왜 실패했는지 알 수 없다 → 리듬 게임에서 가장 치명적인 결함

### 해결 — 판정 수치에서 그림을 역산한다

```
회색 띠 바깥 반지름 = 1 + 판정윈도우 × 속도   (가장 이른 성공)
회색 띠 안쪽 반지름 = 1 − 늦은유예  × 속도   (가장 늦은 성공)
노트 원의 안쪽 테두리 = 노트의 실제 위치
```

- 띠 두께를 **판정 수치에서 계산**하므로 보이는 겹침이 곧 판정이다
- PARRY 스탯을 올리면 **띠가 눈에 띄게 굵어진다** — 성장이 화면에 보인다
- 판정 수치를 나중에 조여도 **그림이 자동으로 따라온다**

> 숫자를 두 곳(로직/뷰)에 적으면 반드시 어긋난다. **한 곳에서 파생시키면 어긋날 수가 없다.**

## 5-3. 어필 기술 ③ — 퍼즐 엔진

순수 C#으로 직접 구현 (외부 매치3 에셋 미사용)

| 기능 | 구현 포인트 |
|---|---|
| **비정형 보드** | 하트·해골 모양처럼 **구멍 뚫린 보드** 지원. 구멍이 대각선 슬라이드를 끊지 않게 처리 |
| **중력 + 대각 슬라이드** | 벽에 얹힌 타일이 대각선 아래로 미끄러진다 → 벽을 우회해 하강 |
| **캐스케이드** | 연쇄 매치 단계별 기록(`CascadeStep`)을 남겨 뷰가 시간순으로 재생 |
| **데드락 검출 + 리롤** | 둘 수 있는 수가 없으면 게임이 멈춘다 → `MoveFinder`로 검출 후 **턴 미소모** 리롤 |
| **고정 보드 모드** | 시드 고정 + 재추첨/리롤 **끄기** (튜토리얼용 스크립트 보드) |

### 뷰와 모델의 분리

> **모델은 이미 완결된 결과를 한 번에 내고, 뷰는 그 기록을 시간순으로 재생만 한다.**

```
PuzzleEngine.Swap(a, b)  →  SwapResult (모든 캐스케이드·낙하·기믹 이벤트가 담긴 완결 기록)
                                    ↓
                         BoardView가 코루틴으로 재생
```

- 연출이 도는 **중에도 모델은 최종 상태** → 연출 길이를 바꿔도 로직이 안 흔들린다
- 연출을 통째로 스킵해도 게임 상태가 동일

## 5-5. 어필 기술 ⑤ — 데이터 주도 설계

### ScriptableObject 10종이 게임의 모든 수치를 갖는다

`StageDataSO` · `BossDataSO` · `TileDefinitionSO` · `PlayerStatsConfigSO` · `DifficultyCurveSO` ·
`RunEconomyConfigSO` · `BossMemorySO` · `PlayerCharacterSO` · `ThemeSO` · `TutorialTopicSO`

### 코드에 고유명사를 적지 않는다

| 나쁜 방식 | 이 프로젝트 |
|---|---|
| `if (stageName == "2-1") ShowChainTutorial();` | `StageDataSO.introduces[]`에 데이터로 |
| 보스별 페이즈 수를 보스 에셋에 하드코딩 | `StageDataSO.battlePhaseLimit` — **판이 정한다** |
| 스테이지별 난이도 표를 손으로 작성 | `DifficultyCurve` — 고리 깊이 × 증가율로 **계산** |

**효과**: 스테이지를 재배치하거나 추가해도 **코드를 한 줄도 안 고친다.**
난이도 표를 손으로 적었다면 스테이지를 늘릴 때 표 갱신을 잊어 새 판만 조용히 물렁해진다.

### 캐릭터 확장도 에셋 추가만으로

캐릭터 = 에셋 1개(`PlayerCharacterSO`). 목록은 `Resources` 스캔.
→ **3번째 캐릭터를 넣어도 코드도 씬 빌더도 안 건드린다.**

## 5-6. 어필 기술 ⑥ — 현지화 (i18n)

- **원천은 구글 시트 → CSV 한 장.** 코드·씬에 문자열 하드코딩 0
- 정적 문구 = `LocalizedText` 바인더 컴포넌트 + 키
- 동적 문구(HP·턴) = `Loc.GetText(key, args)` + `LanguageChanged` 구독해 재렌더
- **함정 하나를 규칙으로 굳혔다**: 동적 문구에 `LocalizedText`를 붙이면 언어 전환 시 **서로 덮어쓴다**

- 툴: `Find Missing Keys In Scene` — 씬을 훑어 CSV에 없는 키를 찾아낸다

## 6. 최적화 & 안정성

### 빌드 용량 / 로딩

| 항목 | 조치 | 효과 |
|---|---|---|
| **BGM 6곡** | **PCM WAV 125MB**(실측) → Streaming / **Vorbis q0.7** | 빌드에 원본 PCM이 통째로 들어가던 것을 차단 |
| **단발 효과음** | **DecompressOnLoad** (스트리밍 금지) | 스트리밍하면 *눌린 뒤에* 소리가 난다 |
| **한글 폰트** | 동적 아틀라스 + **시작 시 일괄 사전 생성** | 용량은 안 늘리고 런타임 끊김만 제거 (↓) |
| **도트 스프라이트** | Point 필터 · 무압축 · 밉맵 끔 | 이중선형 필터로 흐려지는 것 방지 |

### 실기 프레임 — 측정하고 고친 것

**증상**: 안드로이드 실기 빌드에서 프레임이 떨어진다.

| 원인 | 실제로 무슨 일이었나 | 조치 |
|---|---|---|
| **30fps 상한** | `Application.targetFrameRate`를 아무도 안 정했다. 기본값 −1 = "플랫폼 기본값"이고 **모바일에서 그건 30**이다. 모바일은 `vSyncCount`가 무시되므로 이게 유일한 손잡이 | 60으로 고정 |
| **HDR** | 2D 도트에 1을 넘는 밝기가 없는데 렌더 타깃 정밀도만 올라가 대역폭을 먹고 있었다 | URP에서 끔 |
| **동적 폰트 아틀라스** | `ClearDynamicDataOnBuild`라 **빌드에 아틀라스가 빈 채로** 나간다 → 기기에서 한글이 처음 뜰 때마다 SDF를 굽는다. 화면을 넘길 때마다 걸리는 종류의 끊김 | 시작 로딩에서 일괄 생성 |
| **노트 원 텍스처** | 256×256을 비율마다 CPU 루프로 굽는데 그 일이 **전투 첫 2초에 몰린다** | 같이 사전 생성 |

**30fps 상한은 성능만의 문제가 아니었다** — 한 프레임 33ms가
**Lv0 패링 판정 폭(0.25초)의 13%**다. 정확히 눌러도 프레임 경계에 걸려 놓치는 일이 생긴다.
성능 설정 하나가 **게임의 핵심 손맛을 갉아먹고 있었다.**

### 시작 로딩 — "미리 굽는 것"을 어디에 숨길 것인가

런타임에 굽느라 끊기는 것들을 시작할 때 몰아서 굽는다. 설계에서 판단한 것 셋:

- **로고와 겹쳐 돌린다.** 굽는 일을 인트로 뒤에 세우면 대기가 그대로 늘어난다.
  로고가 도는 2.6초 동안 뒤에서 굽고, **끝났는데도 남아 있을 때만** 바를 띄운다
  → **대개는 로딩 바가 안 보이는 것이 정상**이다
- **진행률은 실제 작업 단위로 찬다.** 시간으로 흘리면 느린 기기에서 바가 다 찬 채로 멈춰
  있게 되는데, 그건 "멈췄다"로 읽힌다
- **구울 글자를 정확히 알 수 있다** — 화면 글씨의 원천이 `Localization.csv` 한 장뿐이라
  거기 없는 글자는 게임에도 안 나온다. **실측 343자(한글 274)**.
  현지화를 한 곳으로 묶어 둔 설계가 성능 작업에서 값을 했다

> **사전 생성은 메모리를 더 쓰지 않는다** — 어차피 플레이 중에 만들어지는 것들이고
> 정적 캐시에 남으므로, **만들어지는 시점만** 옮기는 것이다.

**빗나가도 무해하게 설계했다.** 캐시를 데우는 일이라 잘못 짚으면 도움이 안 될 뿐 고장 나지 않는다.
그래서 노트 원의 비율 범위를 `CombatScreen`에서 끌어오는 배선을 **일부러 안 만들었다** —
그 배선이 오히려 깨지기 쉽고, 깨지면 조용히 틀린 값을 굽는다.

### 런타임 안정성

- **널 세이프 슬롯** — 오디오 클립·스프라이트가 비어 있어도 게임이 안 멈춘다
  → **배선이 덜 된 상태로도 플레이 가능** (1인 개발에서 특히 중요)
- **도메인 리로드 OFF 대응** — 정적 서비스 전부에 `[RuntimeInitializeOnLoadMethod] ResetStatics()`
  → 지난 플레이의 상태가 남아 오작동하는 것을 차단
- **세이브 버전 마이그레이션** — `v1 → v2 → v3`, 구버전 세이브 자동 처리
- **모바일 세로/가로** — `OrientationLayout`이 요소마다 프리셋 2벌을 갖고 해상도 변화에 반응
- **`DontDestroyOnLoad`를 2개로** — 정적 서비스 12개는 GameObject가 아니라 `static class`

### 테스트 전략

```
EditMode 163개 — 전부 Core(순수 C#) 대상, 에디터/씬 없이 3초에 완주
```

- **퍼즈 테스트**: 무작위 300턴 시뮬레이션으로 비정형 보드의 낙하/리필 불변식 검증
- **회귀 테스트를 버그마다 남긴다**: 낙하 버그 3종, 고정 보드 6개, 난이도 2개…
- **테스트 가능한 설계가 먼저**: 결정적 tick과 순수 C# Core가 있어서 테스트가 가능해진 것

## 7. 트러블슈팅

### ① 게이지가 줄어들지 않는다 — 3번 재발한 버그

- **증상**: 전투 HP/체간 게이지가 코드상 값은 바뀌는데 화면이 안 줄어듦
- **원인**: `Image.type`이 `Filled`가 아니면 `fillAmount`가 **아무 일도 안 한다**.
  UI 스프라이트를 꽂을 때 Unity가 9슬라이스를 감지해 `Sliced`로 되돌려 놓고 있었다.
  게다가 **`sprite`가 null이면 Image는 언제나 칸을 꽉 채운다**
- **해결**: `CombatScreen`이 `Awake`에서 게이지 3종을 Filled/가로/왼쪽으로 **강제**
- **교훈**: **세 번 재발한 버그는 주의가 아니라 코드로 막는다.** 스프라이트를 갈아 끼워도 안 깨진다

### ② 스테이지 1-2가 빨간 타일로 도배된다

- **증상**: 1-1을 클리어하고 1-2에 들어가면 시작부터 보스 타일이 보드를 뒤덮음
- **원인**: 보스 난입 확률의 입력값인 `TotalSoulsEarned`(= **판 단위** 압박 게이지)를
  성장 캐리 스냅샷에 **실수로 포함**. 1-1에서 쌓인 점수가 1-2로 이월 → 시작부터 난입 확률 최대
- **해결**: 캐리 스냅샷에서 제거, 세이브 v1→v2 마이그레이션, 재발 방지 주석
- **교훈**: 이월 시스템 설계의 핵심은 **"판 단위 값 vs 이월 값"의 구분**.
  이 구분이 흐려지면 증상이 전혀 엉뚱한 곳(보드 도배)에서 나타난다

### ③ 지도 노드와 글자가 23배로 커졌다

- **증상**: 스프라이트 교체 툴을 돌렸더니 월드맵이 폭발
- **원인**: **`SpriteRenderer.drawMode`를 Sliced로 바꾸는 순간 Unity가 트랜스폼 스케일을 `size`로 옮긴다**
  (0.8 → 18.4). 툴이 그 **바뀐 값을 "원래 값"으로 믿고** 곱했다
- **해결**: `git checkout`으로 씬 복구 후, **트랜스폼을 하나도 안 건드리는** 방식으로 재작성
- **교훈**: **원래 값은 눈으로 잰 것 말고 씬 파일(git)에서 확인한다.**
  에디터 툴은 실행 전후를 git diff로 검증하는 습관이 필수

### ④ 보스 타일이 내려오지 않는다

- **증상**: 보스 타일이 보드 중간에 걸려 바닥에 도달하지 못함 → 보스전 진입 불가
- **원인 2가지**:
  1. `BoardRefiller`가 기둥 **중간 빈칸에도** 새 타일을 스폰 → 위 타일이 내려올 자리를 가로챔
  2. **벽에 얹힌 타일이 미끄러질 규칙이 없었다**
- **해결**: 리필을 기둥 최상단 연속 빈칸으로 제한 + 벽 위 타일의 대각선 슬라이드 규칙 추가
- **검증**: **회귀 테스트 3개**를 함께 커밋 (중간빈칸 스폰 금지 / 벽 위 슬라이드 / 슬라이드 구멍 메우기)

### ⑤ 소리가 아예 안 난다 — 배선을 아무리 봐도 없는 원인

- **증상**: 인트로·타이틀에서 BGM이 안 나옴. 클립은 멀쩡히 물려 있음
- **원인**: **해당 씬에 `AudioListener`가 한 개도 없었다.**
  씬 빌더가 카메라에 `Camera` 컴포넌트만 붙이고 있었다
- **해결**: 두 씬에 추가 + **빌더도 함께 수정**해 재발 차단
- **교훈**: **"배선이 맞는데 안 된다"면 한 층 아래(엔진의 전제)를 본다.**
  그리고 수동으로 고쳤으면 **그것을 만든 툴도 같이 고쳐야** 다음에 또 안 사라진다

## 10. 회고 — 가장 크게 배운 것 3가지

### ① 아키텍처는 약속이 아니라 강제여야 한다

"Core에 Unity를 쓰지 말자"는 지켜지지 않는다. `noEngineReferences: true` 한 줄이 그것을 **컴파일 에러**로 만든 순간부터 규칙이 진짜가 됐다.
그 결과 테스트 163개가 **에디터 없이 3초에** 돈다.

### ② 같은 숫자를 두 곳에 적으면 반드시 어긋난다

패링 띠(로직 vs 뷰), 튜토리얼의 밝은 칸과 누를 수 있는 칸, 지도의 길 두께와 노드 크기 —
전부 같은 원인이었다. **한 곳에서 파생시키면 어긋날 수가 없다.**

### ③ 기획 의도를 코드가 배신하는 지점을 찾는 것이 진짜 일

- 잡몹 위협을 **턴**으로 세었더니 *가만히 있는 것이 최적해*가 됐다 → 실시간으로 변경
- 소울을 **클리어한 판에서 0**으로 했더니 *빨리 깬 사람이 손해*를 봤다 → 스테이지별 매장량으로 변경
- 기억(패시브)에 평타 강화를 넣으면 *안 눌러도 세진다* → **"잘 눌렀을 때 더 받는"** 효과만 허용

> 돌아가게 만드는 것과 **의도대로 돌아가게** 만드는 것은 다른 일이었다.
