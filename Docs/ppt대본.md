## 제작 규칙 (반드시 지킬 것)

**형식**

1. **총 17장.** 「챕터 N」 구분 슬라이드는 만들지 않는다.
2. 슬라이드 한 장 = **블록 3개 이하**, 블록 하나 = **2줄 이내**. 넘치면 문장을 줄이지 말고 **덜어낸다**.
3. **제목은 한글 18자 이내.** 그보다 길면 67.5pt 제목이 두 줄로 접혀 상자를 넘친다.
   번호(핵심 구현 ①…)는 제목이 아니라 **부제에** 적는다.
4. **도판은 오른쪽 레일에 세로로 길게** 잡는다(`rail(...)`, 폭 8.2~9.4in × 본문 높이 전체).
   글은 그 왼쪽 칼럼에만 쓴다 — 도판을 아래에 붙이면 자리가 1.5in밖에 안 나와 장식이 된다.
   **왼쪽 칼럼은 폭이 좁으므로 한 장에 카드 2~3장까지**이고, 카드 하나는 2줄을 넘기지 않는다.
5. 표는 4행 이하. 같은 내용을 두 장에 넣지 않는다.
6. 대본에 **없는 문장을 지어내지 않는다.** 수치는 전부 실측값이라 바꾸면 틀린다.
7. 빌드 후 `python validate.py _build.pptx`로 **넘침 0건**을 확인한다.

**내용 — 이 덱의 초점 (2026-08 개정)**

- ✅ **핵심 기능 구현과 알고리즘**이 중심이다: 퍼즐 엔진 3장 · 보드 에디터 2장 · 리듬 전투 2장 · 채보 에디터 1장.
- ✅ **ScriptableObject 에디터 화면을 띄워 놓고 설명한다** — 그래서 「어떻게 구현했는가」가 가장 중요하다.
- ✅ **「무엇을 만들었다」가 아니라 「안에서 어떤 식으로 돌아가는가」**를 적는다 —
  자료구조 · 복잡도 · 왜 그 표현을 골랐는지(CS 근거). 기능 나열과 「밟은 함정」류는 뺀다.
- ❌ 「의존 방향을 컴파일러가 강제한다」 · 「경계를 넘는 방법 3가지」 — **뺐다**(발표에서 설명하기 어려운 주제).
  대신 그 자리에 **데이터 주도(SO)** 한 장을 두고, 「Core가 순수 C#이라 콘솔로 검증했다」는 **13장에서만** 말한다.
- ❌ **30fps 상한(`targetFrameRate`) 이야기는 뺐다** — 최적화라 부르기 민망하다.
  프레임 이야기가 필요한 자리는 10장(결정적 시뮬레이션)이 대신 맡는다.
- ❌ 툴을 지웠다 / 절반을 덜어냈다 / 전·후 비교 — 일체 금지.

# 4장 — 퍼즐 엔진 — 한 번의 스왑

> **부제**: 핵심 구현 ① — 엔진이 결과를 한 번에 끝까지 계산하고, 화면은 그 기록을 재생만 한다.

**`TrySwap(a, b)` 안에서 도는 순서**
두 칸 교환 → 매치 찾기 → 파괴 + 벽 피해 → 중력 · 리필 → 연쇄 반복 → `SwapResult`

**매치 찾기** — 가로 · 세로를 훑어 3칸 이상 이어진 구간(런)을 모으고,
좌표가 겹치는 런끼리 합쳐 **ㄱ자 · T자를 한 그룹**으로 만든다.
파괴 목록은 `HashSet`이라 **교차점이 두 번 세어지지 않는다.**

**되돌리기** — 매치가 없으면 그 자리에서 되돌리고 턴도 안 센다.
그래서 수가 없으면 게임이 멈춘다 → 데드락 검출이 반드시 필요해진다(5장).

**모델 / 뷰** — `SwapResult` 하나에 연쇄 · 낙하 · 기믹이 전부 담긴다.
연출 중에도 모델은 이미 최종 상태 — 건너뛰어도 결과가 같다.

*(영상 5초: 매치 → 연쇄 → 낙하)*

# 5장 — 둘 수 있는 수를 전부 센다

> **부제**: 핵심 구현 ② — 매치 없는 스왑은 턴을 안 먹으므로, 수가 0이면 판이 영영 멈춘다.

**전수 조사 — 스왑 → 판정 → 되돌리기**
후보는 인접한 두 칸뿐이다. 각 칸에서 **오른쪽 · 위 두 방향만** 보면 모든 쌍을 정확히 한 번 센다.
실제로 바꿔 보고 판정한 뒤 **원래대로 되돌린다** — 탐색이 보드를 남기지 않는다.
판정 기준을 엔진의 실제 스왑과 **같은 함수 하나**로 공유한다(따로 적으면 "둘 수 있다고 했는데 못 두는" 유령 수가 생긴다).

**핵심 최적화 — 전체를 다시 훑지 않는다**
전제: 정착이 끝난 보드에는 매치가 하나도 없다.
그러면 새 매치는 반드시 **바뀐 두 칸 중 하나를 지난다** → 전체 스캔 대신 그 칸에서 **네 방향으로 같은 종류를 세는** 국소 검사면 충분하다.
**O(W²H²) → O(W·H·(W+H)).** 9×7 보드에서 약 **8,000 → 2,000 연산**이고, 매 스왑 끝마다 도는 검사다.

**수가 0이면 — 섞는다 (턴은 소모하지 않는다)**
움직일 수 있는 타일만 모아(벽 · 보스 · 부패 · 사슬은 제자리) **Fisher–Yates**로 O(n) 균등 셔플.
난수를 주입받으므로 같은 씨앗이면 그대로 재현된다.
섞자마자 매치가 터져 있으면 공짜 콤보가 되므로 될 때까지 **다시 뽑는다**(거부 표본추출, 최대 32회).
값이 아니라 **`Tile` 객체째** 옮기므로 폭탄 카운트가 따라간다.

# 6장 — 빈칸을 남기지 않는 중력

> **부제**: 핵심 구현 ③ — 벽과 구멍이 뚫린 비정형 보드에서도 성립해야 하는 규칙.

> **불변식** — 정착이 끝나면 **구멍(X) 이외의 모든 칸이 채워져 있다.**

**① 직선 낙하** — 열 안에서 아래로 압축. 구멍은 통과하고 벽 위에는 쌓인다.
**② 대각선 슬라이드** — 벽 그늘에 든 칸은 대각선 위에서 끌어내리고, 벽에 얹혀 못 내려가는 타일은 대각선 아래로.
**③ 리필** — 각 열 꼭대기의 **연속된** 빈 칸만 채운다(중간 빈 칸은 다음 웨이브의 낙하 몫).
**④ 갇힌 칸 끌어오기** — ①~③이 멈췄는데 빈 칸이 남으면, 그 칸에서 **리필이 닿는 자리까지 8방향 너비 우선 탐색**으로
최단 경로를 찾아 길 위의 타일을 한 칸씩 민다. **구멍이 반대로 꼭대기까지 걸어 올라간다.**

**실측 99.08%** — 갇힌 칸의 99.08%가 끌어오기로 메워진다. 제자리 생성은 0.92%(길조차 없는 칸).
경로 탐색은 `Queue` + 「어디서 왔는가」 사전으로 되짚어 만든다.

*(도식: 갇힌 칸 + 길 → 한 칸씩 밀어 메워진 보드 — 슬라이드에 도형으로 그려져 있다)*

# 7장 — 2차원 격자를 저장하는 법

> **부제**: 핵심 구현 ④ — 유니티는 `bool[,]`를 직렬화하지 못한다. 그래서 **눕혀야** 한다.
> *(강사 샘플 「다차원 배열 에디터」에서 가져온 발상. 이 장이 보드 에디터의 뿌리다.)*

**문제** — 유니티 직렬화기는 다차원 배열도 중첩 배열도 저장하지 못한다.
인스펙터에 격자를 띄우려면 **데이터가 먼저 저장 가능**해야 한다.

**표준 해법(평탄화)** — 2차원을 1차원으로 눕히고 번호로 좌표를 되찾는다.
**행 우선**으로 `index = row × width + x`, 역산은 `row = i / width` · `x = i % width`
→ 그래서 **가로 크기를 반드시 같이 저장**해야 한다.

**이 프로젝트** — 행마다 문자열 하나(`string[] boardRows`).
`boardRows[row][x]`는 **같은 행 우선 배치**이고, 다만 그 곱셈을 **문자열 컨테이너가 대신 들고 있다.**

**왜 리스트가 아니라 문자열인가**
① 칸이 **3상태**(O · X · W)라 `List<bool>`로는 못 담는다.
② git diff에 `"OOWOO"`로 **사람이 읽힌다**(원소 63개 리스트는 안 읽힌다).
③ 만들어 둔 스테이지 8개를 옮기지 않아도 된다.

**번호는 이럴 때 쓴다**
드래그로 칠할 때 마지막에 칠한 칸을 **번호 하나**로 비교한다.
런타임은 반대로 편다 — 엔진은 순수 C#이라 **진짜 2차원 `bool[x, y]`**다. 눕히고 세우는 번역은 한 곳뿐.

*(도식: 5×3 번호 격자 — 슬라이드에 도형으로 그려져 있다)*

# 8장 — 격자를 그리고 칠하기

> **부제**: 핵심 구현 ⑤ — 인스펙터의 격자는 위젯이 아니라 **직접 그린 사각형**이다.

**그리기 — 즉시 모드 GUI**
`GUILayoutUtility.GetRect`로 자리 하나를 받고, 각 칸의 사각형을 `x + c × (칸 + 간격)`으로 직접 계산해 채운다.
버튼 63개를 만드는 것이 아니라 **이벤트가 올 때마다 통째로 다시 그린다** — 그래서 칸 크기 · 색 · 브러시를 코드가 전부 정한다.

**칠하기 — 좌표를 번호로**
마우스가 어느 칸인지는 같은 식의 **역산**이다. 누르면 칠하기가 시작되고, 누른 채 지나가면 계속 칠한다.
**같은 칸은 한 드래그에서 한 번만** 처리한다(번호로 비교) — 안 막으면 칸 하나에 Undo 기록이 수십 개 쌓인다.

> **그리는 코드는 한 벌, 편집 상태는 각자.**
> 인스펙터와 전용 창이 같은 그리기 코드를 부르고(브러시를 늘릴 때 고칠 곳이 하나),
> 「지금 어느 칸을 칠하는 중인가」는 창마다 하나씩 들고 넘긴다.
> 저장은 `SerializedObject` 경유라 Undo · 에셋 더티 · 동기화가 공짜다.

*(스크린샷: 인스펙터 격자 + Board Editor 창을 나란히 — 같은 스테이지)*

# 9장 — 리듬 패링 전투 — 채보와 판정

> **부제**: 핵심 구현 ⑥ — 보스 공격은 애니메이션이 아니라 악보다.

**데이터** — 노트 하나 = **타격 시점(박) · 예비동작 길이(박) · 피해.**
패턴 = BPM + 길이 + 노트 목록. **연속기는 별도 타입이 아니라 촘촘히 찍은 노트**다.
페이즈 = HP 구간별 패턴 풀(가중 무작위).

**판정** — `[타격 − 윈도우, 타격 + 유예]` 안의 노트 중 **가장 임박한 하나**를 그 자리에서 지운다.
밖에서 누르면 **헛침** — 잠기고 **보스가 체간을 되찾는다.** 잠금만 있으면 막 눌러도 손해가 없다.

**표시** — 원의 반지름을 진행률이 아니라 **`1 + 남은시간 × 접근속도`**로 정한다.
그래서 회색 띠의 **두께가 곧 판정 폭**이다 — 판정과 그림이 같은 수치에서 나온다.

> **흰 원의 안쪽 테두리가 노트의 위치**이고, 그것이 띠에 겹쳐 있는 동안이 성공 구간이다.

*(영상 5초: 패링 판정 링 + 인살 컷씬)*

# 10장 — 프레임에 기대지 않는 시간

> **부제**: 핵심 구현 ⑦ — 같은 입력이면 프레임레이트가 달라도 같은 결과가 나온다.

**문제** — 매 프레임 `dt`만큼 통째로 굴리면 타격 · 판정 만료 · 예비동작 시작이
**한 프레임 안에 뭉쳐** 순서가 뒤바뀌고, 처리도 최대 한 프레임 늦는다.

```
while (remaining > 0) {
    step = min(remaining, 다음_사건까지, 플레이어_타이머);
    Advance(step);        // 경계까지만 시간을 흘린다
    remaining -= step;
}
```

**방법** — `dt`를 통째로 흘리지 않고 **다음 사건**(예비동작 시작 · 타격 · 유예 만료 · 패턴 종료) **직전까지만** 잘라 진행한다.
**효과** — 시간이 `Tick(초)`로만 흐르고 `UnityEngine`을 안 쓰므로,
패링 · 헛침 · 인살 · 페이즈 전환을 **엔진 없이** 검증한다.

# 11장 — 리듬(채보) 에디터

> **부제**: 핵심 구현 ⑧ — 보스 공격을 그려서 만들고, 플레이하지 않고 들어 본다.

**타임라인**

# 12장 — 현지화 — 원천은 한 장

> **부제**: 원천을 한 곳으로 묶으면, 성능 최적화까지 정확해진다.

**구조** — 원천은 구글 시트 → **CSV 한 장**(139키 × 2언어). 코드 · 씬에 문자열 하드코딩 0.
정적 문구는 `LocalizedText` 바인더 + 키, 동적 문구(HP · 턴)는 `Loc.GetText(key, args)`.

**함정** — 동적 문구에 바인더를 붙이면 언어 전환 시 코드와 컴포넌트가 서로 덮어쓴다.
같은 칸을 여러 문구가 돌려 쓸 때는 **값이 아니라 키를 갈아 끼운다**(`SetKey`).

**툴** — CSV에 없는 키를 쓰는 텍스트를 씬에서 훑어 잡는 메뉴.
원천이 한 장뿐이라 **없는 글자는 게임에도 안 나온다** → 미리 구울 글자를 정확히 센다(343자).

# 14장 — 트러블슈팅 대표 3건

> **부제**: 재발하는 버그는 주의가 아니라 코드로 막는다.

**① 확률의 단위 — 보스 타일이 보드를 도배**
난입 확률이 **리필 타일 하나하나에** 굴려지고 있었다. 한 웨이브에 10칸이면 주사위를 10번.
**"5%"가 실제로는 `1 − 0.95¹⁰ ≈ 40%`였다.** → 동시 상한 + 웨이브 단위 누적 카운터.
**확률은 "무엇 당(per)"인지 반드시 같이 적는다.**

**② 모델은 맞고 뷰가 틀림 — 타일이 옆 열을 가로질렀다**
한 웨이브에서 두 번 움직인 타일(낙하 → 벽에서 대각 슬라이드)의 기록을 `From → To` 하나로 합쳐 뷰에 넘긴다
(중간 좌표가 남으면 뷰가 칸을 잘못 추적한다). 그런데 뷰가 그 두 점을 **직선으로 이어** 타일이 벽을 뚫고 날았다.
→ 뷰가 **꺾인 경로**로 재생하되, 꺾이는 지점에서 속도가 0이 되지 않게 **경로 전체 길이를 하나의 자**로 쓴다.

**③ 3번 재발 — 게이지가 안 줄어든다**
`Image.type`이 `Filled`가 아니면 `fillAmount`가 아무 일도 안 한다.
UI 스프라이트를 꽂을 때 Unity가 9슬라이스를 감지해 `Sliced`로 되돌려 놓고 있었다.
→ `Awake`에서 게이지 3종의 타입을 강제. **세 번 재발했다는 것은 「주의」로는 안 된다는 뜻이었다.**

# 15장 — 최적화 & 런타임 안정성

> **부제**: 최적화가 오히려 화면의 글자를 날린 사고 — 에디터에서는 멀쩡했다.

**글자를 미리 굽게 했더니, 실기에서 일부가 안 보였다**
런타임 끊김을 없애려고 시작 로딩에서 폰트 글자를 한 번에 구웠다. 그런데 아틀라스가 **1024 한 장**이라
386자가 **두 장째로 넘어갔고**, 넘친 글자가 기기에서 안 그려졌다.
그전에는 **화면에 실제로 뜬 글자만** 조금씩 구워져 우연히 한 장에 들어 있었다 — **미리 굽는 행위 자체가 방아쇠**였다.
→ 아틀라스 2048로, 그리고 **두 장을 넘으면 에러 로그**를 남긴다.

| 항목 | 조치 | 이유 |
|---|---|---|
| BGM 6곡 | Streaming / Vorbis | 원본 PCM 20MB × 6이 통째로 빌드에 들어가던 것 차단 |
| 단발 효과음 | DecompressOnLoad | 스트리밍하면 **눌린 뒤에** 소리가 난다 |
| 도트 스프라이트 | Point · 무압축 · 밉맵 끔 | 이중선형 필터로 옆 타일보다 흐려 보이는 것 방지 |

**1인 개발에 특히 필요했던 안정성**
널 세이프 슬롯 · 도메인 리로드 OFF 대응 `ResetStatics()` · 세이브 v1→v3 마이그레이션 ·
정적 서비스 19종 · `DontDestroyOnLoad` 2개

# 17장 — 회고: 가장 크게 배운 것 3가지

"모든 칸이 항상 채워진다"는 주석과 통과 중인 테스트 166개가 오히려 안심시켰다.

**③ 기획 의도를 코드가 배신하는 지점을 찾는 것이 진짜 일**
잡몹 위협을 **턴**으로 세었더니 가만히 있는 것이 최적해가 됐다 → 실시간으로 변경.
소울을 **클리어한 판에서 0**으로 했더니 빨리 깬 사람이 손해를 봤다 → 스테이지별 매장량으로.

> **돌아가게 만드는 것과 「의도대로 돌아가게」 만드는 것은 다른 일이었다.**
